**Blockers**
- **Grain:**
  - The Model SQL groups by `week` and the Load SQL by `shift_id`. Neither column exists in `raw_wms.pick_events`.
  - The plan never says how shift is derived, including shifts that cross midnight.
  - The primary key leaves out `ds`, though the MERGE keys on it.
- **Pick rate:** The model only sums `amount`. There's no denominator, so it isn't a rate yet.
- **Contract:** `owner` is TBD, and there's no contract file.
- **Personal data:**
  - `picker_id` identifies workers and the table measures their performance, so "internal" is the wrong classification.
  - An unsalted SHA256 of a low-entropy ID can be reversed with a dictionary attack.
  - The hashing step isn't in any query, and there's no erasure path.
- **Backfill:** Rollout step 1 is an `UPDATE ... FROM` over two years. An UPDATE can't insert rows into an empty table, and `n` is undefined.
- **Rollback:** There isn't one.

**Should-fix**
- The target table has no DDL, so the MERGE would scan the whole destination on every run.
- The MERGE never deletes shifts that disappear from source.
- There's no cost estimate against the 10 GB dev limit.
- There are no tests and no null policy.
- The 07:00 UTC freshness SLA isn't tied to when shifts end.
- Late-arriving data isn't handled.
- The consumer and the downstream models aren't listed.

**Blockers**

3. **Contract (item 2):** `owner` is `TBD`, which is a required field. No ODCS file is planned, and the change isn't classified as additive or breaking.
4. **Backfill (item 5):** the `UPDATE ... FROM` is malformed. On an empty table it would update zero rows, so it can't backfill anything. It should be a per-`ds` loop that runs the Load MERGE.

**Main "should" findings**
- **Consumer and rate (item 1):** no consumer or decision is named, and a model called "pick rates" only sums `amount`, with no time denominator.
- **Primary key (item 3):** it omits `ds`.
- **Target table (item 6):** `fct_pick_rates` has no DDL. The MERGE `ON` clause won't prune the target, which will fail once a partition filter is required.
- **Deletes (item 5):** the MERGE never deletes, so a shift corrected downward leaves a stale row.
- **Late data (item 11):** nothing covers uploads that arrive after their `ds`.
- **Tests, SLA, downstream, rollback:** no tests, the 07:00 UTC SLA isn't tied to shift upload times, no downstream consumers are listed, and there is no rollback.

The full table in the plan has the required change for each finding, plus two nits.
