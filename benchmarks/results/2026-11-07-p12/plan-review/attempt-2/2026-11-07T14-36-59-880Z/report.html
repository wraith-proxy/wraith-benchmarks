The plan isn't ready to build. It has three blockers and several smaller gaps.

## Blockers

1. **The model SQL uses a column that doesn't exist.** `raw_shop.refunds` has `ds, refunded_at, refund_id, amount`, with no `order_id` (plan.md:26). The Load query uses `refund_id` instead, so the two queries disagree. The stated grain, "one row per refund per ds", matches the Load query, so the Model query looks like the mistake.

2. **The nightly 48-hour replay will double-count, and the load can't be re-run safely.**
   - The same `refund_id` can arrive several times, in the same `ds` or in adjacent ones. `SUM(amount)` then inflates the refund. You probably want to dedupe, for example keep the latest row per `refund_id`, rather than sum. The plan also doesn't say how `ds` relates to `refunded_at`, or whether a replayed refund can land in a different `ds`.
   - The Load is a plain `INSERT INTO` (plan.md:35). Every re-run and every replay appends duplicates. It needs a partition-level overwrite for the `ds` range, either delete and insert or `MERGE`. It also has to reprocess the two replayed days each night, not only `@ds`.

3. **The rollout fails on first build.** Step 1 clones `fct_refunds` (plan.md:49), but a new model has no table to clone. The undo path is also weak.
