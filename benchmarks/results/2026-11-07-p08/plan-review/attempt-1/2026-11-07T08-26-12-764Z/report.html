## Blockers

1. **Retries double-count `amount`.**
   - The source is an SDK upload "retried on bad networks", so the same `event_id` can land more than once.
   - `SUM(amount) ... GROUP BY ds, event_id` adds those duplicates together and overstates revenue.
   - The model should dedupe, for example `QUALIFY ROW_NUMBER() OVER (PARTITION BY event_id ORDER BY event_ts) = 1`. It should not aggregate.
   - A retry can also land in a different `ds`, so `event_id` may repeat across partitions. That conflicts with `primary_key: event_id`.

2. **The load isn't idempotent.**
   - `INSERT INTO ... WHERE ds = @ds` appends every time it runs.
   - Rollout step 2 ("rebuild for the ds range") and any rerun will duplicate rows.
   - Use `MERGE`, or delete and insert by partition (`insert_overwrite`).

3. **The access setup exposes personal data.**
   - `allAuthenticatedUsers` means any Google account, so the data is effectively public.
   - The column list includes `email`, `advertising_id`, `device_id` and `gps_lat/gps_lon`.
   - The contract classifies this as `internal`. It should be personal data or restricted.
   - The plan needs these things:
     - named readers, such as a group
     - policy tags on the personal-data columns
     - a decision on whether those columns belong in staging at all
     - a crypto-shredding or deletion path

4. **The model, the load and the access list disagree.**
   - The model and load output only `ds, event_id, amount`.
   - The Access section lists eight columns.
   - Decide which one is right.

## Should fix

- **`ds` filter mismatch.** The source example filters on `DATE(event_ts) = @ds`, but the model filters on `ds = @ds`. If `ds` is the load date and not the event date, late events land in the wrong day. State what `ds` means and how late data is handled, for example a lookback window.
- **Cost.** The table is about 900 GB, and `SELECT *` with `DATE(event_ts)` can't prune partitions. The plan doesn't declare partitioning or clustering for the source or the target. Specify partition by `ds` (with `require_partition_filter`) and cluster by `event_id`, and add a dry-run bytes estimate.
- **Rollout and rollback.**
  - Row counts alone won't catch the duplicate problem. Compare `COUNT(DISTINCT event_id)` and `SUM(amount)` against the source.
  - You can't restore a snapshot over a live table. Spell out the restore (a clone into place, or a rename).
  - Time travel (7 days) and the snapshot have no stated expiry or cost.
  - Say whether the snapshot is of the whole table or only the affected range.
- **Contract is thin.** It has no schema, types or nullability. It has no quality rules, such as `event_id` not null and unique, or `amount` not null and non-negative if that applies. The `07:00 UTC` freshness SLA doesn't say what it's measured against. The contract also has no retention period and no personal-data fields.
